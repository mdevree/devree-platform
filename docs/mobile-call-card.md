# Mobile call card

MauticCaller 1.1 opens `/mobile/contact-card?id=<Mautic ID>` in its own WKWebView. Staff authenticate with their existing platform account. No shared server secret is shipped in the app. The page is outside the desktop sidebar layout and renders a login form until authenticated. Card API and save API require a staff session; save also validates Origin when supplied.

The card combines current Mautic contact/searcher information, linked project roles/statuses, paginated platform contact history and paginated Mautic notes. Unavailable histories are explicitly marked. Notes are rendered as text, never injected HTML. There are no customer messaging actions.

`POST /api/mobile/calls` requires a stable UUID, selected Mautic ID, direction, original timestamps, nonempty note, connected=true and explicit human contact/conversation confirmation. A technical connection alone can be voicemail; the user must confirm actual conversation. Rejected/missed/unanswered calls must not enter this endpoint. The iPhone observer tracks each call UUID independently, latches connection evidence and keeps pending calls on-device. It does not promise execution while suspended or killed. A separate manual flow is available for genuinely conducted but unobserved calls.

An atomic transaction creates a `Call` (ended/completed, points 0), one `CallNote` and an `AppSetting` delivery record `mobile_call:<UUID>`. The UUID is bound to the first employee and canonical payload hash; changing the contact or note under the same ID returns 409. The existing call-note webhook is intentionally not invoked: this route owns Mautic delivery. There is no `lastActive` rewrite and no inference that the call implies buying interest.

The Mautic call note includes the original event date and a stable `[MauticCaller:<UUID>]` marker. Before creating a note, the service reads **all pages** of that contact's notes to recover an earlier committed request; stalled/incomplete paging stops creation. It reads the saved note back and verifies contact and marker before acknowledging both stores. A timeout/unknown outcome gets a one-minute cooldown before another create. Known Mautic failures return 202 with platformStored=true, mauticStored=false. No false full success. Retry happens when the user reopens/retries the form, not through an unrequested background scheduler; the frozen submission and draft remain on the device. Delivery state can be audited in AppSetting. For extended outages an operator can inspect pending records and retry through the authenticated card.

Accepted note contents are immutable under their request ID. Further edits belong in the regular platform workflow, not in a duplicate mobile call. No database migration or new external service is needed.

Checks: `npm run verify` includes `mobileCalls.test.ts` (missed/unconfirmed rejection, timestamp validation, immutable payload identity, escaped notes, readback failure, cooldown, retry dedupe, Mautic lookup failures). Native CI builds the simulator app and tests independent connected/missed/cancelled call states. Device testing is still required for real carrier events, suspension, lock screen, notification settings and voicemail. The simulator artifact is not a signed iPhone install.
