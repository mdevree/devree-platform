# Automatic WhatsApp housing preferences

Incoming saved messages enqueue a durable AppSetting job. The central n8n worker runs every minute, processes one eligible message per invocation, and recovers missed enqueues using a timestamp/id cursor. It does not send messages, create outreach drafts, or change Realworks saved-search filters.

The authenticated `POST /api/whatsapp/preferences/process` route requires the existing platform webhook secret or a logged-in session. `whatsapp-preference-extract` is a header-authenticated n8n AI gateway using existing OpenAI credentials. Store:false and disabled execution-data persistence limit duplicate transcript storage. Context is the six preceding messages; only literal evidence in the current inbound message can create preferences. Media, ambiguous identities, uncertain/property-specific statements and unsupported preference types require review.

Canonical records: `wa_preferences:<mauticId>` contains source events and effective preferences. They are mirrored to Mautic's existing `zoeker_data` (personalPreferences, activePersonalPreferences) and `ai_profiel_data` (zoekvoorkeuren_uit_gesprekken, actuele_woonvoorkeuren), preserving other fields and Realworks filters. Later explicit corrections supersede earlier values per key. An existing human interpretation of the same message wins. Source messages are treated as data, never instructions. This is AI-assisted extraction with conservative validation, not guaranteed complete interpretation.

Jobs: `wa_preference_job:<messageId>` statuses pending, processed, ignored, review. Failed jobs retain cached extraction and retry with backoff up to one hour; no silent discard. Review jobs retain a reason or extracted review candidates and are available in AppSetting for operator review (no new review UI). No historical bulk backfill: initial cursor starts at activation preparation; only the explicitly requested Gert Jan message was queued separately. Future messages use both the webhook and cursor recovery.

Matching reads effective preferences from canonical records, combines current structural property data with successfully enriched listing text, and marks supported fit, explicit conflict, and unknown separately. Hard conflicts prevent a new opportunity; existing opportunities retain their user-controlled status but receive low priority and an explicit do-not-propose action. Soft conflicts lower priority. Unknown characteristics are not evidence of fit or rejection. Preferences supplement existing Realworks candidate matches; this does not implement a separate search over every unselected property. No artificial interest percentage is added. Opportunity creation is not customer contact, so a seven-day opportunity-creation cooldown is no longer used. Recent contact, active dossiers, completed matters and promises still need review before outreach.

Worker recalculates after updates and every 15 minutes to include new enrichment. Mutation ingestion also recalculates. Distributed locks serialize the worker and WhatsApp/Realworks profile merges; lease is ten minutes to recover crashed workers. Mautic requests are bounded. Monitor pending age, review/error jobs, latest matching timestamp, and central n8n executions. Retry a reviewed job only after resolving its identity/media ambiguity. To stop processing, deactivate the central worker and disable the inbound enqueue or leave queued jobs durable. The AI gateway alone cannot write profiles or contact customers.

Validation: `npm run verify`; `src/lib/whatsappPreferences.test.ts` covers source grounding, soft vs hard wording, ambiguous scope, chronological corrections, missing features, explicit absence, mixed descriptions, numeric requirements and idempotent interpretation. Production verification must read back the canonical record, Mautic mirror, unchanged Realworks data and matching reasons. Never test through a WhatsApp sending route.
